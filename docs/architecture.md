# Architecture — Appwrite continuation

Next.js App Router server components preserve the existing responsive Tailwind/UI. `src/lib/appwrite/server.ts` owns node-appwrite clients: API-key-backed TablesDB for trusted server data access, anonymous Account for signup/verification, and cookie/session Account for identity verification. The API key never crosses a client boundary. SDK transport uses an environment-aware Undici proxy dispatcher with inherited TLS verification and NO_PROXY support; it never disables trust checks.

`requireUser` calls Account.get for each protected request/action. `requireResident` additionally verifies the private profile/onboarding. Proxy only adds no-store headers; cookie presence alone is not authorization. Account.createEmailPasswordSession produces the secret for an HttpOnly, SameSite=Lax session cookie; production adds Secure and __Host-. Cookie expiration follows Appwrite's session expiration. Logout revokes the current Appwrite session before clearing the cookie. Registration/profile initialization is idempotent; an existing account can recover a transient profile-creation failure by logging in. Email verification uses Appwrite's userId/secret flow with a trusted canonical origin.

Domain authorization lives in CityService, independent of SDK/network. Verified actor identity, not submitted user/author/role fields, controls all writes. City and joined membership are checked before publishing/commenting. Only authors edit/delete their content; hidden/deleted content cannot be restored by author edits. Reports are not available through user-readable data endpoints; moderator identities are server-provisioned. Appwrite transactions cover onboarding, content mutations and report resolution; conflict/failure propagates safely rather than falling back to nontransactional writes.

AppwriteRepository maps actual inspected column aliases to typed domain rows. A request-scoped cache parallelizes metadata inspection across the seven existing tables. The gate requires safe table permissions, available compatible columns and unique profile/membership indexes; no tables are automatically created or weakened. The trusted-server-only policy prevents direct clients from spoofing ownership fields. Details and exact backend operations are in BACKEND_REQUIREMENTS.md.

The UI retains RU/KK server locale cookie, persists authenticated preference and restores it on login. Content is rendered as escaped text. City/feed/membership/profile queries are scoped server-side. Feed/comment pagination uses newest-first system timestamps plus ID ordering. Lists are bounded (initial seven communities, max 100 discovery/memberships, max 30 onboarding choices); growing beyond those limits requires explicit pagination/cursor work, not silently treating a truncated list as all data. Private profile fields are projected out of public author display.

`/demo` uses fictional fixtures only. Browser tests instead use scripts/appwrite-fixture.ts, a loopback API contract fixture never imported by the application. Security tests exercise CityService/schema checks and transaction calls; neither constitutes live Appwrite acceptance. Supabase SQL is historical, archived under docs/legacy-supabase; no runtime fallback exists.
