# Architecture — Appwrite continuation

Next.js App Router server components preserve the existing responsive Tailwind/UI. `src/lib/appwrite/server.ts` owns node-appwrite clients: API-key-backed TablesDB for trusted server data access, anonymous Account for signup/verification, and cookie/session Account for identity verification. The API key never crosses a client boundary. SDK transport uses an environment-aware Undici proxy dispatcher with inherited TLS verification and NO_PROXY support; it never disables trust checks.

`requireUser` calls Account.get for each protected request/action. `requireResident` additionally verifies the private profile/onboarding. Proxy only adds no-store headers; cookie presence alone is not authorization. Account.createEmailPasswordSession produces the secret for an HttpOnly, SameSite=Lax session cookie; production adds Secure and __Host-. Cookie expiration follows Appwrite's session expiration. Logout revokes the current Appwrite session before clearing the cookie. Registration/profile initialization is idempotent; an existing account can recover a transient profile-creation failure by logging in. Email verification uses Appwrite's userId/secret flow with a trusted canonical origin.

Domain authorization lives in CityService, independent of SDK/network. Verified actor identity, not submitted user/author/role fields, controls all writes. City and joined membership are checked before publishing/commenting. Only authors edit/delete their content; hidden/deleted content cannot be restored by author edits. Reports are not available through user-readable data endpoints; moderator identities are server-provisioned. Appwrite transactions cover onboarding, content mutations and report resolution; conflict/failure propagates safely rather than falling back to nontransactional writes.

AppwriteRepository maps actual inspected column aliases to typed domain rows. A request-scoped cache parallelizes metadata inspection across the seven existing tables. The gate requires safe table permissions, available compatible columns and unique profile/membership indexes; no tables are automatically created or weakened. The trusted-server-only policy prevents direct clients from spoofing ownership fields. Details and exact backend operations are in BACKEND_REQUIREMENTS.md.

The UI retains RU/KK server locale cookie, persists authenticated preference and restores it on login. Content is rendered as escaped text. City/feed/membership/profile queries are scoped server-side. Feed/comment pagination uses newest-first system timestamps plus ID ordering. Lists are bounded (initial seven communities, max 100 discovery/memberships, max 30 onboarding choices); growing beyond those limits requires explicit pagination/cursor work, not silently treating a truncated list as all data. Private profile fields are projected out of public author display.

`/demo` uses fictional fixtures only. Browser tests instead use scripts/appwrite-fixture.ts, a loopback API contract fixture never imported by the application. Security tests exercise CityService/schema checks and transaction calls; neither constitutes live Appwrite acceptance. Supabase SQL is historical, archived under docs/legacy-supabase; no runtime fallback exists.

## Public visual MVP

The public root and /demo render the existing CityApp client boundary; all real Appwrite routes keep their server authentication/authorization. /demo?page= selects feed, communities, community, post, create, profile, saved or about, with id for a community/post. Next links provide history/back/forward navigation and reset page-local filters when the route key changes. No browser component imports server SDK code.

src/lib/demo.ts owns bilingual fictional seed content using existing community IDs. src/lib/demo-store.ts provides a versioned, validated localStorage external store with server hydration defaults, cross-tab subscriptions and a memory fallback when writes are blocked. Demo posts/comments/likes/bookmarks/memberships and profile edits never reach Appwrite; themes and locale survive reload. Locale also updates the existing city-locale cookie for real account pages. Scoped .mvp CSS tokens isolate light/dark public styling from authenticated screens. Locally shipped media needs no CDN. No infrastructure or database changes are required for this frontend.

## Social MVP 2.0

CityApp retains the existing shell, route selection, create form, search, community discovery and bookmarks. SocialPost, Conversation, SocialProfile, Notifications and TrustControls are separate client components under src/components/social, sharing the existing scoped light/dark tokens. The /demo segment has localized loading and recoverable error boundaries. Native dialogs provide focus trapping, Escape dismissal and focus restoration; ordinary buttons/links and details retain keyboard semantics.

The existing storage key is migrated additively: old profile fields, owned posts, bookmarks, memberships and comments remain. New state adds username/district, following/mute/block arrays, comment author/parent/tombstone metadata, notifications and local reports. Parsing rejects invalid ownership, cycles, cross-post parent references and invalid event dates. This is a resilience boundary for a local demo, not real server authorization. All existing server guards remain independent.

For You ranking is deterministic: +20 for joined community, +8 for followed author, up to +12 recency points (one per hour relative to the newest available post), +2 for a current local like and +1 per nondeleted locally written comment. Ties sort by actual stored timestamps. Sample likes/follower/community-size numbers do not influence ranking or appear as real popularity. City and joined-community feeds sort chronologically. Hidden authors are excluded from all post lists; quoted hidden content is replaced by an unavailable message. Sample events do not mutate engagement counters.

Reply parents use stable IDs; deleting an owned parent with children leaves a tombstone. Only locally owned comments have edit/delete controls. Indentation is capped at two levels while arbitrary reply targets remain linked structurally. Author profiles and quotes use the existing demo query routes. Locally created links require that browser's storage; missing content provides recovery navigation.

Notifications are a bounded (100-entry) local activity journal with a sample flag, explicit event type, read state and local target. There is no polling, background generation or real delivery. Local report creation never calls Appwrite. Mute keeps follow state; block also removes the local follow. Both can be reversed from the own profile.

The city catalog uses broad administrative districts and does not request location permissions. Sample district assignments are fictional. Shymkent timestamps use an explicit UTC+05 clock and typed RU/KZ month names, avoiding server/browser ICU differences that caused a hydration error during testing. Fixed sample dates remain visibly dated. The city authority reference is https://www.gov.kz/memleket/entities/shymkent?lang=ru; a fresh fetch was denied (403) by this session's network policy, so no live authority-page verification is claimed.
