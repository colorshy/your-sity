# Architecture — Milestone 3

Next.js 16 App Router serves authenticated server components. `src/proxy.ts` uses @supabase/ssr to refresh cookies through validated Auth requests. It preserves refreshed cookies on the response and disables response caching. Proxy is not the authorization boundary: `requireUser()` verifies every protected server page/action with `auth.getUser()`. `requireResident()` verifies a profile exists and onboarding is complete. Server actions independently authenticate, validate bounded inputs and rely on PostgreSQL RLS. No service-role client exists.

`src/lib/supabase/server.ts` supplies a cookie-bound server client; `browser.ts` supplies the public client factory for future interactive work. Public configuration rejects secret-key roles. Sessions survive browser reload through SSR cookies. PKCE `/auth/callback` accepts only fixed local destinations; `/auth/confirm` allows only email verification tokens. Errors return generic localized responses, without exposing provider error details or account-existence information. Supabase provides Auth rate limiting; production should configure SMTP/CAPTCHA/rate settings for expected traffic.

Real feature pages and components live under src/app and src/components/backend. Feed uses the resident city, optional joined-community filtering and newest-first created_at/id ordering, 20-item pages. Community/profile detail shows the newest 20 posts. Profile UI is own-account only; publicly queried author fields contain no email or private Auth metadata. City selection and memberships are saved atomically by complete_onboarding RPC. City changes after selection require administrator work to preserve membership invariants.

RU/KK server UI uses a cookie-backed locale and paired translated messages via src/lib/locale.ts; the HTML language updates on locale change. Existing demo state/localStorage remains isolated under /demo. There is no fixture-data fallback on live routes. Missing configuration, loading, empty and provider-error states are distinct. Feature forms show pending state and enforce browser + server validation.

SQL controls authorization even when requests bypass the UI. Security-definer functions have an empty search_path, explicit relation names and restricted execute privileges; moderator membership is in a dedicated non-public schema and cannot be self-assigned. Reports have no general update grants. Moderator queue/resolution UI, real publishing UI and discussions remain later work.

Tests separate real local PostgreSQL policy execution from mocked Auth/browser transport. The loopback fixture is imported only by test scripts, never application code. Deployment requires real Supabase migrations/configuration and hosted smoke tests before claiming readiness.
