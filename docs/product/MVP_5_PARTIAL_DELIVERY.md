# MVP 5 implementation and migration gate

This branch implements the authenticated navigation shell and live card actions over the existing eleven-table model. The layout uses real membership and community rows. The feed reads likes, published comments and the viewer's bookmarks in bounded batches, then applies existing hidden-author filtering. Like and bookmark writes still go through the authenticated `postInteraction` server action. Share builds the post URL from the current origin. No new Appwrite or Vercel resource was created.

## Additive model required for the remaining features

Do not apply this plan to the shared Frankfurt project until its actual metadata and existing rows have been exported, a restore has been rehearsed in isolation, and an authorized operator approves the change. The existing user and post must remain untouched.

1. Add a private, row-security-enabled `post_reposts` table: `user_id` and `post_id` required strings, created timestamp, deterministic ID from the existing `membershipId(user, post)` pattern, and indexes on `post_id`, `user_id` and unique `(user_id, post_id)`. Server-only writes should validate a visible published source and resident identity; undo must verify ownership. Counts should exclude hidden users and hidden/deleted sources. Test duplicate submission, concurrent submit, block/mute, moderation, undo and rollback against an isolated clone.
2. Add an Appwrite Storage bucket dedicated to post images: private read/write by default, allow JPEG/PNG/WebP, maximum 5 MiB per file, no browser API key. Server upload flow must verify the actual byte signature and decoded image, authenticated resident and post ownership, enforce four files per post and prepare short-lived upload ownership. The storage policy must not grant public writes. Define explicit authorized read behavior for published posts, with hidden/deleted content inaccessible.
3. Add a private `post_media` table with `post_id`, `file_id`, `owner_id`, `position`, `mime`, `bytes`, timestamps and unique `(post_id, position)`/`file_id` indexes. A draft/upload record must expire and be cleaned if publishing fails. Deletion and moderation should first hide media access, then delete storage objects through a retryable cleanup job; log and retry partial failures. Editing must preserve committed associations until replacements are validated.
4. Add dry-run schema and bucket inspection, comparing exact permissions, attributes and indexes before any mutation. Apply only missing additive resources in an isolated project, export and restore existing data, test negative access from another user, then obtain approval for the shared Preview project. The application must tolerate legacy text-only posts throughout rollout and rollback.

The described repost and media model is a plan, not an applied migration or working feature. Do not expose UI controls for it until the backend and access tests pass. Hosted acceptance, data residency review and public invitations remain blocked.
