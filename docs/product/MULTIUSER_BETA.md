# MVP 3 — controlled multi-user beta

Status: implementation in `feat/mvp-3-multiuser`, based on MVP 2.1 `929245e2d9fe44098461b55b2064b6e4c4268b61`. Hosted Appwrite migration and live acceptance remain separate gates. No production deployment or Vercel project change is included.

## Runtime behavior

The public `/` and `/demo` remain explicitly fictional, browser-local demos, preserving `your-city-demo-v2`. Real-account views `/feed`, `/communities`, `/create`, `/posts/<id>`, `/people/<id>`, `/profile`, `/saved` and `/notifications` use verified Appwrite sessions and shared server data exclusively. Backend errors never substitute demo data/localStorage. Reads refresh on navigation/reload; real-time subscriptions/push are not implemented.

Existing signup/login/persistent HttpOnly sessions, profile name/language editing, onboarding and membership remain. Failed login/profile initialization clears the newly issued session cookie and attempts session revocation. Every protected action calls Account.get, validates all resource IDs, derives actor identity from that account, checks city/ownership and uses existing fail-closed production Firewall controls. The only supported beta city is Shymkent.

- Likes and private bookmarks use one deterministic record per account/post. Displayed like totals come from shared records, not seed counts. Only the owner can list their bookmarks.
- Asymmetric follows, mute and bilateral blocks use account-owned connections. Blocking removes follows in both directions. Mutes hide content for the viewer; blocks exclude both participants from one another's feed/detail/comment/interaction/notification access. Preferences can be removed from the viewer's profile. Blocking is reversible; it does not delete anyone's content or automatically restore follows.
- Threaded comments store an immutable same-post parent ID. Parent must be published and accessible at creation. Edited/deleted comments require ownership; deleted parents retain redacted tombstones for visible replies. Paginated threads show reply context, including an unavailable/previous-page parent, and cap indentation for phones. Moderators can hide a reported comment without hiding its entire post.
- Likes, follows, comments and replies create recipient-owned, server-derived notifications in the same transaction. No self notifications; muted/blocked senders are excluded. Deterministic notification IDs prevent repeat-toggle spam. Moderated/deleted/inaccessible post/comment targets are removed from notification results. Notification rows never contain body excerpts or private profile fields.
- For You reuses the deterministic MVP 2.1 ranking with shared memberships/follows/own likes/bookmarks/comments and freshness. City remains chronological; Communities contains joined-community posts. Privacy and moderation filtering precede ranking and pagination. No inferred location or GPS; neighborhood is unused until real profiles have a verified optional district contract.

## Capacity and operational limits

This beta intentionally bounds each complete queried dataset to fewer than 1000 rows; privacy lists never silently truncate. Reaching that safety limit returns an error and requires bounded indexed/cursor query work before increasing beta capacity. For You ranks at most 200 recent eligible posts, then paginates the ranked snapshot within that window. City/Mine use 20 visible rows plus one lookahead. With fixed candidates/signals/now ranking is deterministic; new content or changed signals can move offset pages. Large-feed cursor/snapshot consistency and load testing remain pre-expansion work.

The existing Vercel Firewall auth/write rules must be configured and exercised on an authorized non-production target. Every new mutation uses the write guard; production missing-rule/provider failure denies writes. Local fixture mode is deliberately not evidence of production rate limiting. No in-process limiter is claimed to protect a distributed deployment. Signup abuse, actual mail delivery, rate thresholds, moderation staffing and consent/data-retention policy need real beta acceptance.

## Migration gate

Apply [the additive migration manifest](../migrations/MVP_3_APPWRITE.md) through authorized administration of the existing project/database. New private tables: post_likes, bookmarks, connections, notifications. Existing nullable additions: comments.parent_id, reports.comment_id and server-owned profiles.social_version. Social mutations update participant profile fences within their transaction so concurrent blocks and interactions contend on shared rows; actual Appwrite conflict detection must still pass live acceptance. Do not recreate populated resources or assign fictitious owners/statuses. Metadata gates reject incompatible tables/indexes/permissions before normal account operations. Until the migration is available, this code must not replace an operating deployment.

## Automated verification

`npm run test:security`, `npm run test:social`, `npm run test:operations`, `npm run test:deployment`, lint, typecheck, build, and `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium npm test` exercise the service and loopback SDK fixture. The local memory and SDK fixtures reject conflicting snapshot commits rather than overwriting another transaction; this models fail-closed behavior, not actual Appwrite isolation. The new browser scenario uses two distinct registrations and isolated contexts; verifies shared posts/likes, private bookmarks, replies, recipient notifications/read state, follows, mute/block/unblock, independent logout and 320px layout. These are **local fixture tests**, not hosted integration.

`npm run test:live` runs the same two-browser interaction smoke against a separately authorized HTTPS beta target, without starting a fixture or server. Configure BETA_BASE_URL, BETA_EMAIL_A/B, BETA_PASSWORD_A/B securely for two disposable already onboarded Shymkent accounts, and BETA_ALLOW_WRITES=1. The runner exits 2 without network requests when inputs/authorization are absent. Do not place credentials in CLI arguments or Git. The flow creates one uniquely marked test post, likes/bookmarks/comments/replies/follows and temporary mute/block preferences; it attempts to soft-delete the test post in finally. It removes likes/bookmarks and follows through unblock on success. It may leave residual test connections on failure and retains soft-deleted thread/notification history by design. Use dedicated test accounts, inspect residual state and revoke their sessions after acceptance. Do not run against Production.

## Required live acceptance before students join

1. Record authorized beta URL, code SHA, actual Appwrite metadata/query preflight, transaction create/rollback, and all additive migration operations. Verify private table/row reads and writes are denied directly to anonymous AND session clients. Do not treat local schema fixtures as proof of this.
2. Run the HTTPS two-account smoke above, plus third-account and cross-city ownership/visibility denial tests, forged IDs/roles and expired/revoked sessions. Verify signup, mail verification and onboarding against hosted Auth independently (the live smoke signs into prepared accounts).
3. Exercise simultaneous likes/follows, concurrent block vs reply/like, duplicate retries, provider failure and notification rollback. Appwrite must reject conflicting transactions; no unprotected retry or fallback is allowed. Confirm the actual query indexes, nullable fields and transaction semantics match SDK 31.2.0.
4. Use a trusted configured moderator to process post/comment reports; confirm hidden content cannot reappear in feeds, saved posts, notifications or author edits. Test abuse limits and unavailable-rule denial with the actual Vercel Firewall.
5. Review RU/KZ, 320px devices, accessibility, real content/privacy notices, moderation ownership and account/data retention with the cohort organizer. Begin with a small consenting student cohort only after recording successful live results.
