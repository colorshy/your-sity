## Operational behavior and limitations

/api/health is liveness only. /api/ready returns minimal 200/503 status after configuration, schema/permission gate, required city/community records and representative read-query/index checks. Its backend result is cached per process for 30 seconds and is not a transaction/Auth/email/Firewall-action or full acceptance test. Rule IDs being present does not prove live rules work; mutation checks do that separately. No live readiness result has been observed here.

The official @vercel/firewall checker uses a trusted VERCEL_URL destination and inherited request headers; request Host is never the destination. All mutating server actions except logout are checked. Logout remains available to revoke sessions even during limiter outages. The email confirmation endpoint returns 429/503 on protection refusal. Development tests are explicitly distinguished from enforced production limits. Missing Vercel runtime metadata denies production mutations. There is no in-memory production fallback.

Operational JSON logs contain only enumerated event/result/kind and timestamp, not credentials, cookies, request bodies, IPs, emails or raw provider errors. Authentication attempt success/failure and readiness/abuse checks are logged. Security response headers protect framing, MIME sniffing, base/form/object embedding and verification-token referrers; they do not constitute proof against every XSS/abuse scenario.

.github/workflows/ci.yml runs only non-secret local/fixture checks with read-only GitHub permissions; it does not deploy or contact the real backend. CI execution is not claimed verified merely because the workflow was pushed. Vercel/account access and real backend verification remain external blockers, not an application test failure.
